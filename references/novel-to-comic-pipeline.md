# 小说改 AI 漫剧模式

当用户上传小说全本，或要求把小说转换为整书解析、故事圣经、全集分集表、逐集剧本、逐集分镜、连续性检查、图片、配音、字幕或剪辑工程时读取本文件。这个模式负责长期项目状态和阶段交付；普通单次 ComfyUI 提示词任务不加载本文件。

## 核心原则

- 整本小说用于建立全局理解，剧本、分镜和媒体生产按集推进。
- 原著正文是事实源；用户明确批准的改编决定可以覆盖原著，但必须登记，不能悄悄改写。
- 不依赖聊天上下文保存全书信息。把事实、改编决定和每集结束状态写入项目文件，每次续作前读取它们。
- 每条重要人物事实、事件、伏笔和改编决定尽量保留原著章节或段落编号，无法定位时标为待核实。
- “已生成文件”“已生成图片”“已完成配音”“已建立剪辑工程”都必须有实际产物。只有方案、提示词或清单时，准确称为交接文件。
- 默认先做一集完整样片闭环，经用户确认后再批量生产，避免错误扩散到全集。

## 启动与默认设置

先确认 Agent 能否读取用户上传的小说。可读取时直接开始入库；不可读取时只请用户重新上传、提供本地路径或换成可读取格式，不要假装看过全文。

记录以下项目设置。用户没有指定且不会改变故事方向时，可以声明默认值后继续，不必把所有问题一次问完：

- 作品名和原著文件。
- 改编忠实度：忠实、平衡、自由；默认“平衡”。
- 单集目标时长；默认 2—3 分钟。
- 集数：用户指定或根据剧情密度自动规划；默认自动规划。
- 画幅与平台；默认竖屏 9:16 短视频。
- 视觉风格、目标受众、语言、旁白比例和内容尺度。
- 最终图片/视频工作流、配音工具和剪辑工具；到对应生产阶段再确认也可以。

如果缺少的选择会明显改变全集结构，例如目标集数、单集时长或是否允许合并角色，先询问并暂停结构改编。其他设置可以写入 `assumptions`，让用户之后修正。

## 阶段 0：原著入库与索引

1. 保留原文件，不覆盖、不润色原著。
2. 提取可检索文本，保留卷、章和段落层级；必要时生成 `normalized-novel.md`。
3. 给章节和段落稳定编号，例如 `V01-C003-P012`。`source-index.jsonl` 记录编号、标题、原文件位置和简短内容说明。
4. 长篇小说按卷或章节分块读取，但不得只根据局部摘要下全书结论。所有分块完成后做一次跨卷汇总，检查人物同名、化名、时间跳跃、伏笔回收和结局信息。
5. 记录无法解析的页面、缺章、乱码、图片文字或附件，不得用模型臆造缺失内容。

质量门：章节顺序完整，全文可追溯，缺失内容已列明。未通过时不进入全集结构规划。

## 阶段 1：整书解析与故事圣经

先生成 `whole-book-analysis.md`，包括：一句话故事、类型与受众、主题、世界观、主线与支线、人物弧、冲突升级、情绪曲线、爽点或泪点、结局、影视化优势、改编难点和风险。

再生成可长期复用的事实库：

- `story-bible.md`：世界规则、时代、地点体系、叙事口吻、核心主题、主线、不可破坏的因果、允许改编项和已批准改编决定。
- `characters.json`：角色 ID、姓名与别名、年龄阶段、身份、外貌锚点、服装变化、性格、目标、能力、关系、人物弧、首次/末次出现和 `source_refs`。
- `locations.json`：地点 ID、空间结构、时代、地标、光线、关联事件和 `source_refs`。
- `props.json`：道具 ID、外形、材质、尺寸、归属、能力、出现/转移/损坏记录和 `source_refs`。
- `relationships.json`：关系双方、关系类型、公开与隐藏状态、变化节点和 `source_refs`。
- `timeline.json`：故事内时间、事件、人物年龄或状态、地点、因果和 `source_refs`。
- `clue-ledger.json`：伏笔 ID、首次埋设、表面解释、真实含义、允许揭晓点、实际回收点、重要度、禁止提前泄露项和 `source_refs`。

事实不确定时使用 `unknown` 或较低 `confidence`，不要填补原著没有的信息。发现原著自身矛盾时列入问题单，请用户决定采用哪一版。

质量门：主要角色、结局、跨卷时间线和关键伏笔均已覆盖；每个关键事实可追溯到原著或用户批准的改编决定。

## 阶段 2：全集分集表

不要机械执行“一章一集”。根据目标时长和戏剧密度重组为“开场钩子—冲突升级—转折或高潮—结尾卡点”，同时保留原著因果和伏笔顺序。

同时导出 `episode-plan.csv` 与 `episode-plan.json`。每集至少包含：

```text
episode_id｜title｜source_range｜target_duration｜opening_hook｜episode_goal
core_conflict｜mid_turn｜climax｜ending_hook｜character_state_change
clues_planted｜clues_paid_off｜must_keep｜adaptation_changes｜production_notes
```

生成 `coverage-audit.md`，检查：

- 主线和必要支线是否都有归属集。
- 关键角色的出场、退场和成长转折是否完整。
- 伏笔没有提前揭露，回收没有丢失。
- 相邻集的开场、结尾和人物状态能够衔接。
- 没有为追求卡点破坏人物动机或因果。
- 集数与目标时长大致可行。

把全集分集表作为门控文件。用户未批准或仍有结构性冲突时，不批量生成逐集剧本。

## 阶段 3：逐集剧本

每次生成某一集前读取四类内容：故事圣经与事实库、该集分集条目、对应原著片段、上一集结束状态与未决连续性问题。第一集没有上一集状态时使用项目初始状态。

`script.md` 面向人阅读，`script.json` 面向后续自动化。剧本至少包含：

- 集号、标题、目标时长、原著范围和本集改编说明。
- 3—8 秒开场钩子、场景顺序、冲突升级、高潮和结尾卡点。
- 每场的时间、地点、出场人物、剧情目的、动作、对白、旁白、音效、音乐意图和来源编号。
- 角色的进入状态、离开状态，以及本集新增或回收的伏笔。
- 不得在这一集透露的秘密和必须保留到后续的状态。

对白要可表演、可配音，旁白只承担画面和对白难以表达的信息。用目标语速检查台词量和预计时长；超时应删减或拆集，不能简单加快全部配音。

质量门：剧情目标与分集表一致，关键事件有原著来源，时长可行，人物动机成立，结尾状态已明确。

## 阶段 4：逐集分镜

只根据已批准剧本生成分镜。导出 `storyboard.csv` 和 `storyboard.json`，每个镜头至少包含：

```text
shot_id｜scene_id｜start_time｜duration｜narrative_purpose｜shot_size
camera_angle｜camera_move｜character_action｜expression｜location｜props
dialogue_or_narration｜sfx_music｜transition｜asset_refs｜source_refs
start_state｜end_state｜image_prompt｜video_prompt｜negative_prompt
```

镜头时长总和应接近剧本目标时长。相邻镜头必须能解释人物位置、视线、动作、服装、伤势和道具去向。不要为每个镜头重新描述一个不同角色；提示词引用稳定的角色、场景和道具资产 ID。

第一次进入图片生产前，读取 `visual-asset-storyboard.md`：先建立人物、场景和道具资产卡并通过主视觉基准板，再批量生成镜头。具体提示词语法以用户确认的 ComfyUI 工作流和 `prompt-rules.md` 为准。

## 阶段 5：连续性检查

连续性检查分三层：本集内部、相邻集衔接、全书事实与伏笔。生成 `continuity-report.md`，按“阻断、重要、建议”标记问题，并给出证据文件和来源编号；不要只写笼统的“可能不一致”。

至少检查：

- 人物身份、年龄、称呼、外貌、服装、伤势、位置、知识范围和能力上限。
- 地点结构、昼夜、天气、行程耗时和事件顺序。
- 道具归属、持握手、数量、损坏、丢失和再次出现。
- 关系变化、人物动机、秘密知情范围、伏笔埋设与回收。
- 剧本时长、镜头时长、对白与画面对应、字幕遗漏或提前。
- 改编新增内容是否与后续原著冲突。

阻断问题修复后才批准本集。批准时写入 `state-after-episode.json`，更新角色、地点、道具、关系、伤势、秘密、伏笔和时间线状态；把跨集未决问题追加到 `08_reports/continuity-issues.json`。

## 阶段 6：图片、配音、字幕和剪辑交付

### 图片与视频

从已批准分镜和三类资产生成 `image-prompts.csv`，记录镜头 ID、工作流、节点、资产引用、正/负向提示词、种子或版本和输出文件名。只有真实运行工作流并检查结果后，才把图片登记为已生成。失败重跑遵守单变量原则，并保留失败版本。

### 配音

先建立角色声音表，记录说话人、年龄感、音色、语速、情绪范围、发音表和禁用风格。`voice-lines.csv` 至少包含集号、场次、镜头、说话人、台词、情绪、预计时长、音频文件名和状态。存在可用 TTS 工具且用户允许执行时生成实际音频；否则只导出配音清单与工具填写说明。

### 字幕

字幕以批准的对白和最终音频时长为准，导出 UTF-8 `SRT`；需要样式时另导出 `ASS`。检查时间码递增、无重叠、说话内容无遗漏、断句自然、单条不过长。音频尚未生成时，只能输出待对齐字幕草稿并标明状态。

### 剪辑工程

先生成 `edit-decision-list.csv` 和 `timeline-manifest.json`，记录轨道、素材文件、入点、出点、转场、字幕、音效、音乐和镜头 ID。只有存在对应剪辑工具、格式支持且实际创建成功时，才交付可打开的剪辑工程；否则提供可导入素材目录、时间线清单和明确的导入步骤，不要伪造 `.prproj`、`.drp` 或其他工程文件。

所有媒体文件使用稳定命名，例如：

```text
EP001_S003_SH005_image_v02.png
EP001_S003_SH005_voice_LINFAN_v01.wav
EP001_subtitles_zh-CN_v01.srt
```

## 阶段 7：整包验收与下一步引导

完成当前阶段后更新 `deliverables-manifest.json`，记录文件路径、版本、状态、依赖和最后检查时间。最终 `final-qc.md` 至少核对：

- 原著覆盖与已批准改编。
- 剧本、分镜、图片、音频、字幕和剪辑清单的镜头 ID 一致。
- 所有阻断级连续性问题已关闭。
- 没有缺失素材、空占位文件或未说明的草稿。
- 用户能从 `NEXT_STEP.md` 看懂下一步。

每次回复末尾只给当前最有用的下一步：需要用户确认时指出具体文件和决定；可以继续执行时告诉用户回复“继续生成第 N 集”或直接进入下一阶段。不要一次抛出整条流水线让零基础用户自行判断。

## 对用户的阶段汇报格式

小说模式每次完成工作后，用以下短格式汇报；没有的项省略：

```text
当前阶段：
已完成：
生成文件：
发现的问题：
下一步：
```

只有在相应文件真实存在或内容已经完整交付时，才能列入“已完成”。
